# 外部レビュー用ステージング環境について

このドキュメントは、外部エンジニアによるセキュリティ・DB設計レビュー用に作成された
ステージング環境の案内です。**本番環境とは完全に別のインフラ(別のSupabaseプロジェクト・
別のVercelプロジェクト)で、実在の顧客データ・個人情報は一切含まれていません。**

## 環境情報

- ステージングURL: `https://salon-management-staging.vercel.app`
- 本番URL(`https://salon-manager.net`)とはVercelプロジェクト・Supabaseプロジェクトの
  両方が完全に別物です。ステージング側での操作・変更が本番に影響することはありません。
- ステージングのSupabaseプロジェクトは本番と同じ`supabase/migrations/`配下のマイグレーション
  一式をそのまま適用しているため、テーブル構成・RLS(Row Level Security)ポリシーは本番と
  同一です。

## 今回のレビュー範囲

- セキュリティ全般(認証・認可・RLS・入力検証・Edge Functionsの実装)
- DB設計(スキーマ・インデックス・RLSポリシーの妥当性)
- **Stripe(決済)連携は対象外です** — 現時点でStripe連携は未実装で、`companies`テーブルに
  将来用のプレースホルダー列(`stripe_customer_id`/`stripe_subscription_id`)があるのみです。
  決済フロー・Webhookは今回のレビュー対象に含まれません。
- AI機能(AIチャット・AI広告評価)は、ステージングでは意図的にAPIキー未設定のため動作しません
  (本番キーを流用しないための措置)。これらの機能はレビュー対象外としてご了承ください。

## テストアカウント

ログイン情報(メールアドレス・パスワード)は、このドキュメントとは別の安全な手段で
共有者から直接お渡しします。役割と用途は以下のとおりです。

| ロール | 所属 | 用途 |
| --- | --- | --- |
| system_admin | 全社横断 | 全会社・全店舗の管理者権限での確認 |
| company_admin (会社A) | ステージング検証サロンA | 1社内の管理者権限、店舗2件の切替確認 |
| store_manager (会社A) | ステージング検証サロンA・本店/ステージング支店 | 割当店舗の範囲確認 |
| staff (会社A) | ステージング検証サロンA・本店のみ | 単一店舗への権限スコープ確認 |
| company_admin (会社B) | ステージング検証サロンB | 会社A/B間のcompany_id分離確認用の別テナント |

会社Aには売上・目標・固定費のダミーデータが入っており、ダッシュボード・損益表・月締め等が
実際に動作する状態です。会社Bは分離確認用の別テナントとして最小構成です。

## 確認していただきたい観点(例)

- 認証: 他ユーザーのメールアドレス/パスワードでのログイン試行、セッション・トークンの扱い
- 認可: 各ロールが本来アクセスできないページ・操作にAPI直叩きで到達できないか
- RLS: `company_id`/`store_id`を跨いだデータの読み取り・書き込みがAPI経由で可能でないか
  (会社Aのアカウントで会社Bのidを指定してリクエストする、等)
- Edge Functions(`supabase/functions/`): service role keyの扱い、入力検証、認可チェック
- DBスキーマ・RLSポリシー(`supabase/migrations/`): 設計上の妥当性、欠けている制約の有無

## 注意事項

- ステージング環境のデータは検証用です。自由に操作・削除して問題ありません。
- 見つかった問題は、実際の脆弱性かどうかに関わらず、報告いただけると助かります。
- 本番環境への一切のアクセス・操作は不要です。本番URLへはアクセスしないでください。
